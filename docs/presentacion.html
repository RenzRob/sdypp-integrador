El Problema

El mercado de tickets está roto

Tres problemas estructurales que ninguna plataforma centralizada resuelve hoy:

📈

Reventa sin control

Los revendedores compran tickets en masa mediante bots y los ofrecen a precios 3x o 5x el valor original, sin ningún mecanismo que los limite. Las plataformas obtienen comisión en ambas ventas, sin incentivo a frenarlos.

Sin techo de precio
🔄

Doble venta con QR

Una persona compra un ticket, captura su código QR y lo vende múltiples veces. El primer comprador ingresa, los demás quedan en la puerta. El sistema no distingue quién es el dueño legítimo en tiempo real.

Anti-replay inexistente
🏢

Plataformas centralizadas

Ticketmaster, StubHub, etc. son la única fuente de verdad. Pueden modificar datos, cancelar ventas, retener dinero o cambiar las reglas unilateralmente. No hay auditoría pública ni inmutabilidad.

Sin transparencia · Sin auditoría
La Solución

Blockchain propia por evento

¿Por qué blockchain?

  • Cada evento tiene su propia cadena de bloques: todas las transacciones (compras, reventas, transferencias) quedan registradas de forma inmutable desde el día 0.
  • Las reglas del evento (precio máximo de reventa, límite de transferencias, modo nominado) se graban en el bloque génesis y no pueden modificarse.
  • Cualquier auditor puede verificar el historial completo de un ticket, desde su emisión hasta el ingreso al evento.
  • No existe una entidad central que pueda alterar los datos: el consenso PoW valida cada bloque.

Cómo resuelve cada problema

  • Reventa sin control → La regla precio_max en el génesis limita el precio de reventa al X% del original. El sistema rechaza cualquier listing que lo supere.
  • Doble venta QR → El QR es un JWT de 60 segundos firmado con un secreto único por ticket. Al transferir, el secreto se elimina. El scanner verifica firma + propietario actual + flag anti-replay.
  • Plataformas centralizadas → La blockchain es la fuente de verdad. Nadie, ni el admin, puede modificar un bloque ya minado.

Mensajería

RabbitMQ: colas y flujo de datos

transactions_q
Cola de transacciones confirmadas
Quién publica: transaction-api, cada vez que el usuario confirma un pago.
Quién consume: NCT (Node Coordinator).
Objetivo: notificar al NCT que hay una nueva transacción lista para ser incluida en un bloque, sin que la API espere a que eso suceda.
mining_gateway_q
Cola de tareas de minería
Quién publica: NCT, cuando forma un bloque candidato con ≥5 txs o tras 10 segundos.
Quién consume: Mining Gateway (vía PULL del Transaction Pool con mTLS).
Objetivo: entregar el bloque candidato y el rango de nonces al cluster de minería externo sin exponer RabbitMQ a Internet.
mining_tasks (local)
Cola de subtareas por worker
Quién publica: Transaction Pool, al dividir el rango de nonces entre los workers disponibles.
Quién consume: Workers CPU y GPU (en el cluster de minería).
Objetivo: paralelizar el cómputo MD5 distribuyendo rangos de nonces distintos a cada worker para que no repitan trabajo.
nct_results_q
Cola de bloques resueltos
Quién publica: Worker (el primero que encuentra el nonce válido), vía Transaction Pool → Mining Gateway → RabbitMQ GKE.
Quién consume: NCT.
Objetivo: devolver el bloque minado al NCT para que lo valide y lo persista en Redis. Con ACK explícito: si el bloque es inválido, NACK y no se persiste.
Flujo completo
tx-api → transactions_q → NCT → mining_gateway_q → Gateway
TrP (PULL mTLS) → mining_tasks → Workers
Workers → nct_results_q → NCT → Redis blockchain:{eid}
¿Por qué no llamadas directas entre servicios?
  • Desacoplamiento: la API confirma la compra al usuario en <100ms. Que el bloque tarde 10s en minarse no bloquea nada.
  • Durabilidad: si el NCT cae, los mensajes esperan en la cola. No se pierde ninguna transacción.
  • ACK explícito: un bloque inválido recibe NACK y nunca se persiste en la blockchain.
Comunicación entre clusters

Cuándo, cómo y por qué es segura

¿Cuándo se comunican?

  • Solo cuando el Transaction Pool (cluster-mining) necesita una nueva tarea de minería: hace GET /next-task al mining-gateway (GKE) cada ~20 segundos.
  • Cuando un worker encontró el hash válido: el TrP envía POST /result al mining-gateway con el bloque resuelto.
  • No hay comunicación inversa: GKE nunca inicia conexiones al cluster de minería. El modelo es 100% PULL.
NCT → queue:mining → mining-gateway ← GET /next-task ← TrP → workers
mining-gateway ← POST /result ← TrP
mining-gateway → queue:nct_results → NCT

¿Por qué es segura?

  • mTLS mutuo: el mining-gateway exige que el TrP presente un certificado de cliente firmado por la CA interna. Ambas partes se autentican.
  • CA propia: generada con gen-certs.sh. La CA no está en git. Los certs se cargan como K8s Secrets.
  • HTTPS end-to-end: el tráfico viaja cifrado sobre Internet. No hay posibilidad de intercepción o spoofing.
  • Sin exposición de RabbitMQ: el broker nunca tiene puerto público. El gateway actúa como proxy seguro entre clusters.
CA interna Cert cliente (TrP) Cert servidor (gateway) HTTPS + TLS 1.3
Seguridad

¿Qué es mTLS y por qué importa?

TLS normal vs mTLS mutuo

TLS estándar (HTTPS)
  • Solo el servidor presenta certificado
  • El cliente no se autentica criptográficamente
  • Cualquiera puede hacer una request al endpoint
mTLS mutuo
  • Servidor y cliente presentan certificado
  • La CA valida ambos lados del handshake
  • Si el cert de cliente no es de nuestra CA: conexión rechazada
En TicketChain: solo el Transaction Pool (cluster k3s del profe) tiene el certificado de cliente firmado por nuestra CA. Un atacante externo que intente hacer GET /next-task al mining-gateway recibe un error TLS y la conexión se cierra. Ni siquiera llega a la aplicación.

Implementación en el proyecto

  • Frontend + APIs: HTTPS con certificado Let's Encrypt, gestionado automáticamente por cert-manager en GKE. Dominio: ticketchain404.duckdns.org
  • Mining gateway (servidor): cert firmado por la CA interna, SAN = IP pública del gateway. Cargado en K8s Secret gateway-tls.
  • Transaction Pool (cliente): presenta trp.crt en cada request. Cargado en Secret trp-tls en el cluster k3s.
  • Validación cruzada: cada lado verifica la CA del otro con cross-cluster-ca Secret. Ni el gateway acepta certs externos, ni el TrP acepta gateways falsos.
Let's Encrypt → Frontend/APIs CA interna → Inter-cluster
Decisión de Diseño

¿Por qué no exponer RabbitMQ directamente?

❌

Si RabbitMQ estuviera expuesto a Internet

  • Cualquier actor malicioso podría publicar tareas de minería falsas o bloques inválidos directamente en la cola.
  • Podría consumir tareas legítimas antes que los workers reales, frenando el pipeline.
  • El protocolo AMQP no tiene autenticación criptográfica a nivel de red: depende solo de usuario/contraseña, expuesta en texto cifrado pero sin verificar la identidad del cliente.
  • Los ataques de amplificación y denegación de servicio son triviales contra un broker de mensajería público.
✅

Con el modelo PULL + mining-gateway

  • El broker nunca tiene puerto público. Solo es accesible dentro del cluster.
  • El único endpoint público es el mining-gateway, protegido con mTLS. Solo el TrP legítimo puede conectarse.
  • El gateway valida que el resultado que llega por POST /result tiene el hash correcto (dificultad 3) antes de enviarlo a la cola nct_results_q.
  • Superficie de ataque mínima: un solo endpoint, con autenticación criptográfica bilateral, que además valida el trabajo antes de aceptarlo.

Redis Master + Réplica + Sentinels

Redis Master (:6379)
Acepta todas las escrituras y lecturas. Tiene AOF (Append Only File) habilitado: cada operación se persiste en disco antes de confirmar. Si cae, los datos no se pierden.
Escritura Lectura AOF persistence
Redis Réplica (:6380)
Copia sincrónica del master. Sirve lecturas para distribuir carga. Si el master cae, Sentinel promueve la réplica a master en segundos, sin intervención manual.
Lectura Failover target
Sentinel 1 (:26379)
Monitorea master y réplica. Vota en el quorum para declarar failover.
Sentinel 2 (:26380)
Para failover se necesitan mayoría de votos (≥2 de 3). Elimina split-brain.
Sentinel 3 (:26381)
Tres sentinels garantizan quorum incluso si uno cae. Número impar obligatorio.
Flujo de failover: Un sentinel detecta que el master no responde → aguarda el timeout configurado → inicia una votación entre los 3 → si la mayoría coincide → el sentinel líder promueve la réplica a master → notifica a los servicios con la nueva dirección → el sistema continúa operando en segundos. Los servicios usan la dirección del Sentinel, no del master directamente: siempre saben a quién conectarse.

Minería

Ciclo de minería — Proof of Work

PASO 1 — ACUMULACIÓN
NCT acumula transacciones
El Node Coordinator (Python) consume de transactions_q vía RabbitMQ. Cuando acumula ≥5 transacciones o pasan 10 segundos, forma un bloque candidato con el prev_hash del último bloque de la cadena.
PASO 2 — DISTRIBUCIÓN
NCT publica tarea global
Publica en mining_gateway_q el bloque candidato con rango de nonces: nonce_start=0, nonce_total=10M. El Transaction Pool hace PULL cada ~20s con mTLS.
PASO 3 — DIVISIÓN
TrP divide entre workers
El Transaction Pool subdivide el rango de nonces entre los workers disponibles (CPU y GPU) y publica subtareas en la cola local mining_tasks.
PASO 4 — POW
Workers: MD5 masivo
Cada worker itera nonces en su rango. Calcula MD5(bloque + nonce). Si el hash comienza con "000" (dificultad 3): publica resultado en nct_results_q.
PASO 5 — VALIDACIÓN
NCT verifica y persiste
El NCT recibe el bloque resuelto, re-verifica el hash localmente, lo persiste con RPUSH blockchain:{event_id} en Redis y actualiza los owners. ACK. Bloques inválidos reciben NACK.

Algoritmo PoW

# Pseudocódigo del worker
nonce = nonce_start
while nonce < nonce_end:
  data = json.dumps(block) + str(nonce)
  hash = md5(data.encode()).hexdigest()
  if hash.startswith("0" * difficulty): # "000"
    block["nonce"] = nonce
    block["block_hash"] = hash
    publish_result(block) # → nct_results_q
    return
  nonce += 1

Worker GPU vs CPU

  • Worker GPU (CUDA/C): paraleliza el cómputo MD5 en miles de hilos CUDA. Procesa rangos de nonces en un kernel con implementación md5.cuh custom.
  • Worker CPU (Python): usa hashlib.md5 con múltiples procesos. Complementa la GPU o actúa como fallback si no hay GPU disponible.
  • Dificultad configurable: variable de entorno MINING_DIFFICULTY=3 en K8s. En producción: 3 ceros de prefijo MD5.
  • Clusters separados por diseño: el cluster de minería puede tener hardware especializado (GPU) sin afectar la latencia de los servicios de usuario.

Valor para el usuario

Lo que TicketChain garantiza desde el primer bloque, sin confiar en nadie:

🔍
Transparencia total
Toda la historia de un ticket — compras, reventas, transferencias — es visible y auditable por cualquiera. La cadena es pública.
🚫
Imposibilidad de doble venta
El QR es un JWT de 60s firmado con secreto único por ticket. Al transferir, el secreto se destruye. El scanner verifica propietario actual + flag anti-replay.
💰
Precio máximo de reventa garantizado
La regla precio_max está en el bloque génesis (inmutable). El sistema rechaza cualquier listing que la supere. No hay excepciones.
📱
QR dinámico y seguro
El QR se auto-refresca cada 30 segundos. Un captura de pantalla caduca en 60s y no puede reutilizarse. El dueño actual siempre tiene el QR válido.
📷
Validación en puerta
El staff escanea el QR con cualquier celular. Respuesta en milisegundos: verde (acceso), rojo (expirado, ya ingresó, dueño distinto). Sin apps especiales.
♻️
Mercado secundario transparente
La reventa existe dentro del sistema, con precio visible, sin intermediarios opacos. El comprador sabe exactamente cuántas veces se revende el ticket.
📜
Reglas inmutables desde el día 0
El organizador define las reglas en el génesis. Nadie — ni el admin — puede cambiarlas después. La confianza no depende de una empresa.
