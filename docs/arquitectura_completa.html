Arquitectura y Procesos de TicketChain

Guía visual detallada para estudiar la interacción entre microservicios, bases de datos (Redis/Postgres), Blockchain y pasarelas de pago.

1. Topología de Red y Componentes Principales

TicketChain es un sistema distribuido orientado a microservicios. Se utiliza Nginx como API Gateway para enrutar las peticiones al servicio correspondiente. La persistencia se divide en almacenamiento relacional (PostgreSQL), caché ultrarrápida (Redis) y persistencia distribuida (Blockchain).

2. Flujo de Negocio: Compra Oficial (Mercado Primario)

Este flujo describe qué ocurre cuando un usuario compra un ticket directamente al organizador del evento.

Puntos de Control: Se verifica que el evento no esté suspendido y que queden tickets en el "Pool" disponible. Si el evento es "Nominado" (intransferible o de 1 solo ticket por usuario), se revisa que el comprador no tenga ya una entrada.
sequenceDiagram autonumber actor Comprador participant T as Transaction API participant R as Redis participant MP as Mercado Pago participant MQ as RabbitMQ Comprador->>T: Solicita Comprar Ticket Oficial (POST /buy) T->>R: ¿Quedan tickets en el Pool del evento? alt Evento Agotado R-->>T: Pool Vacío T-->>Comprador: Error (Sold Out) else Hay disponibilidad R-->>T: Extrae ID de Ticket disponible (LPOP) Note over T,R: Bloqueo de concurrencia T->>R: Reserva el Ticket a nombre del usuario (TTL: 15 mins) T->>MP: Genera Link de Pago MP-->>Comprador: Muestra pantalla de pago Comprador->>MP: Paga MP->>T: Webhook (Aprobado) T->>R: Asigna propiedad definitiva del ticket T->>MQ: Envia evento de tipo 'buy' para minar en Blockchain T-->>Comprador: Ticket Asignado Exitosamente end

3. Flujo de Negocio: Reventa (Mercado Secundario P2P)

Uno de los valores agregados más importantes de TicketChain es el control del mercado secundario mediante Smart Contracts y Reglas de Negocio en caché.

Reglas Dinámicas de Reventa: Antes de permitir listar o comprar en reventa, el sistema valida que no se supere el "Precio Máximo" permitido por el organizador, que no se exceda el "Límite Máximo de Reventas" por ticket, y que la "Ventana de tiempo" no haya cerrado.
sequenceDiagram autonumber actor Vendedor actor Comprador participant T as Transaction API participant R as Redis participant MP as Mercado Pago participant MQ as RabbitMQ Note over Vendedor,T: Fase 1: Listar Entrada Vendedor->>T: Quiero revender mi entrada (POST /list) T->>R: Valida Propiedad del ticket T->>R: Valida Reglas (Precio Máx, Límite Reventas) alt Rompe Reglas (ej: Revende muy caro) T-->>Vendedor: Error 409 (Regla de negocio violada) else Cumple Reglas T->>R: Crea la oferta en la lista de reventas (HSET) T-->>Vendedor: 200 OK (Publicado) end Note over Comprador,T: Fase 2: Compra de Entrada Usada Comprador->>T: Compra entrada del listado (POST /buy-listed) T->>R: Bloquea entrada temporalmente T->>R: Oculta la oferta del listado (HDEL) T->>MP: Genera Link de Pago por el precio de reventa Comprador->>MP: Paga MP->>T: Webhook (Aprobado) Note over T,R: Transferencia P2P T->>R: Saca ticket de la billetera del Vendedor T->>R: Mete ticket en la billetera del Comprador T->>R: Incrementa el contador de reventas del ticket T->>R: Resetea el "Secreto QR" por seguridad T->>MQ: Envia evento tipo 'resell' (From: Vendedor, To: Comprador)

4. Minería de Contratos Inteligentes

El minado en Blockchain es lento e impredecible. Por eso, el Transaction API no se comunica directamente con Ethereum, sino que delega el trabajo pesado a los Workers a través de RabbitMQ.

sequenceDiagram autonumber participant MQ as RabbitMQ (Cola) participant W as Worker (CPU) participant R as Redis (Estado) participant P as Transaction Pool participant G as Mining Gateway participant BC as Smart Contract (Blockchain) MQ->>W: Entrega evento ('buy' o 'resell') W->>R: Actualiza estado a 'processing' W->>P: Envia TX para ser agrupada (Batching) loop Cada X Segundos G->>P: Pide transacciones pendientes P-->>G: Lista de TXs G->>BC: Interactúa con Smart Contract (minteo o transferencia) BC-->>G: Transacción Minada (Hash) G->>P: Notifica éxito y limpia el pool end G->>R: Actualiza estado a 'mined' G->>R: Guarda el TX_HASH para el usuario

5. Validación Offline con QR Dinámico (TOTP)

Para evitar fraudes (capturas de pantalla) y permitir escaneos rápidos incluso sin internet, TicketChain utiliza el algoritmo TOTP (Time-based One-Time Password), el mismo que usa Google Authenticator.
