📝 Registro de usuario

Un usuario nuevo envía email y contraseña. El sistema valida, hashea la contraseña con bcrypt, genera una wallet address derivada del ID, persiste en PostgreSQL y devuelve un JWT.

Solo administradores pueden crear eventos. El sistema valida los datos, crea el bloque génesis de la blockchain del evento, inicializa todos los tickets en Redis y los encola en el pool de disponibles.

🎟️ Compra de entrada (venta primaria)

El flujo de compra tiene dos fases: primero se reserva el ticket con un TTL de 15 minutos, luego el usuario confirma el pago en el checkout. Si el evento es "nominada", solo se permite una entrada por usuario.

🏷️ Publicar entrada en reventa

El dueño de un ticket puede publicarlo en el mercado secundario respetando las reglas del evento: precio máximo, límite de reventas, ventana de tiempo y si la entrada es nominada (en ese caso la reventa está prohibida).

📱 Generar código QR

El titular del ticket solicita su QR para ingresar al evento. Se genera un JWT de corta duración (60 segundos) firmado con un secreto único del ticket. El frontend auto-refresca el QR cada 30 segundos.

GET /transactions/qr-token/:event_id/:ticket_id transaction-api Redis JWT 60s QRCode library
Diagrama de secuencia
sequenceDiagram autonumber actor U as Titular del ticket participant FE as Frontend participant GW as Nginx participant TX as Transaction API participant RD as Redis U->>FE: Abre "Mis Entradas" → "Mostrar QR" FE->>GW: GET /api/transactions/qr-token/{event_id}/{ticket_id}

secret, {expiresIn: 60}) TX->>TX: Genera URL:
"{origin}/scan?token={jwt}" TX->>TX: QRCode.toDataURL(url) TX-->>FE: 200 {token, qr_image (base64), expires_at} FE-->>U: Muestra QR en pantalla loop Auto-refresh cada 30s FE->>GW: GET /api/transactions/qr-token/… GW->>TX: Nueva solicitud TX->>TX: Nuevo JWT con mismo secret TX-->>FE: 200 nuevo token FE-->>U: QR actualizado end end

⛏️ Ciclo de minería de bloques

El NCT (Node Coordinator) acumula transacciones confirmadas y forma candidatos de bloque. Las tareas de minería se distribuyen al cluster de minería via un gateway con mTLS. Los workers CPU/GPU resuelven el Proof of Work.

(:8000) participant MQ2 as RabbitMQ

routing_key: tx.new loop Acumula transacciones NCT->>NCT: pending_txs.append(tx)

OR timer >= BLOCK_TIMEOUT (10s) NCT->>NCT: Determina event_id dominante NCT->>RD: LINDEX blockchain:{event_id} -1 RD-->>NCT: último bloque JSON NCT->>RD: LLEN blockchain:{event_id} RD-->>NCT: next_index NCT->>NCT: Crea bloque candidato:

🗄️ Modelo de datos — Redis

Redis es la fuente de verdad del estado activo del sistema. Todas las claves se organizan por namespace. Cada namespace tiene un color identificador; los tipos de dato Redis están codificados con badges de color.

STRING LIST HASH SET TTL 900s
Namespace  event:
Key Pattern Tipo Descripción TTL Ejemplo de valor
event:{event_id} STRING Objeto evento completo serializado como JSON — {"name":"Rolling Stones 2026","date":"2026-10-15T20:00:00Z","venue":"Luna Park","total_tickets":5000,"price":15000,"status":"active","rules":{"precio_max":50,"max_reventas":3,...},"genesis_block_hash":"000a4f2e..."}
events:list LIST Índice global de IDs de todos los eventos (LPUSH al crear) — ["a1b2c3d4", "e5f6a7b8", "c9d0e1f2"]
event:{event_id}:available_tickets STRING Contador de entradas disponibles. DECR al comprar, INCR al cancelar. — "4985"
event:{event_id}:listings HASH Tickets en reventa. Field = ticket_id, Value = JSON del listing. — field "T000042" → {"seller_wallet":"0xab12ef34","price":18000,"listed_at":"2026-08-10T...","resale_count":1}
event:{event_id}:tickets:pool LIST Cola FIFO de IDs de tickets sin dueño disponibles para LPOP al comprar. — ["T004997", "T004998", "T004999", "T005000"]
Namespace  ticket:
Key Pattern Tipo Descripción TTL Ejemplo de valor
ticket:{event_id}:{ticket_id}:owner STRING Dueño actual del ticket. Tres estados posibles. 900s si pending "0xab12ef34" "null" "pending_payment"
ticket:{event_id}:{ticket_id}:resales STRING Contador de reventas realizadas. INCR en cada transferencia. — "2"
ticket:{event_id}:{ticket_id}:qr_secret STRING Secreto único (32 bytes hex) para firmar y verificar JWTs de QR. Se elimina al transferir. — "a3f9d2e18b4c5f670c1d2e3f4a5b6c7d8e9f0a1b"
ticket:{event_id}:{ticket_id}:checked_in STRING Timestamp del primer ingreso al evento. Ausente = no ingresó. Anti-replay flag. — "2026-10-15T20:15:30Z"
Namespace  user:
Key Pattern Tipo Descripción TTL Ejemplo de valor
user:{wallet_address}:tickets SET Set de entradas del usuario. Cada elemento es la clave compuesta "{event_id}:{ticket_id}". — {"a1b2c3d4:T000042", "a1b2c3d4:T000087", "e5f6a7b8:T001324"}
Namespace  pending_tx:
Key Pattern Tipo Descripción TTL Ejemplo de valor
pending_tx:{tx_id} STRING Transacción en espera de confirmación de pago. Expira si el usuario no confirma. TTL 900s {"tx_id":"uuid","type":"buy","event_id":"a1b2c3d4","ticket_id":"T000042","wallet_address":"0xab12ef34","price":15000,"event_name":"Rolling Stones 2026"}
Namespace  txpool:
Key Pattern Tipo Descripción TTL Ejemplo de valor
txpool:{event_id} LIST Cola de transacciones confirmadas esperando ser incluidas en un bloque. El NCT las consume vía RabbitMQ. — ["{tx_buy_json}", "{tx_resell_json}", "{tx_buy_json2}"]
Namespace  blockchain:
Key Pattern Tipo Descripción TTL Ejemplo de valor
blockchain:{event_id} LIST Cadena de bloques del evento. Index 0 = génesis. RPUSH al minar. LINDEX -1 para el último bloque. — ["{genesis_json}", "{block_1_json}", "{block_2_json}", "{block_3_json}", ...]

📊 Métricas HTTP & RabbitMQ

Cada request HTTP que llega a transaction-api o access-control incrementa el contador http_requests_total (prom-client). Prometheus recoge ese valor cada 15 segundos. RabbitMQ expone métricas de sus colas en tiempo real mediante su exporter built-in.

prom-client http_requests_total rabbitmq exporter queue depth HPA metrics
